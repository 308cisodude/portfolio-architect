# Internationalization model

Portfolio Architect separates machine data, Home Assistant translations, and static Lovelace presentation. No translated string is used as a provider identity, target identity, file path, policy rule, routing input, or calculation key.

## Machine layer

The calculation engine emits language-neutral keys and states. Stable user-owned target IDs, provider IDs, policy rule IDs, allocation states, WKNs, and ISINs do not depend on display language. The historical `fund_id` key remains only a compatibility alias for the same stable target identity.

## Home Assistant entity layer

Entity names, enum states, state-attribute labels, config/options flows, and icons use Home Assistant translation keys. Native entity states therefore follow the active user's frontend language independently of the static dashboard view language.

## Static dashboard layer from v1.63.0

Dashboard behavior is authored once under `dashboard/src/shared/`. User-facing Lovelace strings live in matched locale catalogs under `dashboard/src/i18n/`. Technical locale differences that are not translations live in bounded JSON-Pointer overlays under `dashboard/src/overlays/`.

The current EN/DE source has 100 matched translation keys. English is the structural base with an empty technical overlay; German uses 40 bounded technical overlay operations. Build tooling resolves the selected catalog and overlay and emits conventional static YAML. Home Assistant never sees `$i18n` markers and runs no generator or locale-selection code.

Installable repository outputs are:

- `dashboard/generated/portfolio-architect-dashboard-en.yaml`;
- `dashboard/generated/portfolio-architect-dashboard-de.yaml`;
- `dashboard/generated/portfolio-architect-dashboard-en-de.yaml`.

`dashboard/bilingual-dashboard.yaml` remains a byte-identical compatibility alias for the combined EN/DE artifact. The combined dashboard keeps EN first and DE second. A single-language installation can instead load only EN or DE, so future locales do not add runtime Lovelace weight to users who do not select them.

`tools/build_dashboard.py` is deterministic and release packaging fails if committed generated output differs from a fresh build. `tools/scaffold_dashboard_locale.py` creates a new catalog with explicit `__TODO__` values and an empty overlay; incomplete catalogs are rejected rather than silently falling back to English.

## View-language isolation

Home Assistant translates native entity states according to the active user profile, not the selected Lovelace view. Static view-local wording is therefore kept in locale catalogs where needed. Machine states remain language-neutral. Target-position state text that would otherwise depend ambiguously on the profile language stays hidden where the presentation relies on state-driven icons and view-local legends.

The language shortcut badge continues to open `/profile/general` when changing Home Assistant's own entity-state localization is desired. Portfolio Architect does not write profile settings or persist a shared dashboard-language helper.

## Security and stability rationale

The localization design uses only static native Lovelace output. It does not inject JavaScript, create helpers, call services, write Home Assistant profile settings, add frontend plugins, or introduce a runtime template/include dependency. Locale generation is an offline release/development concern and is covered by deterministic semantic regression tests.
